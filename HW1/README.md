# ВышКат

Домашнее задание № 1 по конструированию программного обеспечения.

Консольное приложение на C# для учёта транспорта и вещей. Транспорт принимается в парк после техосмотра. Программа показывает инвентарные номера, количество предметов, суммарное суточное потребление энергии и транспорт для новичков.

## 1. Запуск

Требуется .NET SDK 10.0. Оба проекта используют `net10.0`. Для первого восстановления пакетов тестового проекта нужен доступ к NuGet либо уже заполненный локальный кэш.

Все команды ниже выполняются из корня репозитория, в котором находятся папки `HW1` и `HW1.Tests`.

Восстановление зависимостей обоих проектов и сборка приложения:

```bash
dotnet restore HW1.Tests/HW1.Tests.csproj
dotnet build HW1/VyshKat.csproj
```

Запуск консольного меню:

```bash
dotnet run --project HW1/VyshKat.csproj
```

Запуск готовой демонстрации без пользовательского ввода:

```bash
dotnet run --project HW1/VyshKat.csproj -- --demo
```

Запуск тестов:

```bash
dotnet test HW1.Tests/HW1.Tests.csproj
```

Запуск тестов со сбором покрытия:

```bash
dotnet test HW1.Tests/HW1.Tests.csproj --collect:"XPlat Code Coverage" --results-directory HW1.Tests/TestResults
```

Отчёт `coverage.cobertura.xml` появится во вложенной папке `HW1.Tests/TestResults`. Эта папка, а также `bin` и `obj`, исключена из Git через `.gitignore`.

## 2. Возможности и демонстрация

Приложение поддерживает:

- добавление транспорта с предварительной проверкой сервисным центром;
- отказ в приёме неисправного транспорта;
- добавление вещей на баланс;
- подсчёт всех принятых предметов;
- суммирование потребления всех принятых потребителей энергии;
- выборку транспорта с удобством для новичков не ниже 6;
- получение названий и инвентарных номеров всех принятых предметов.

При обычном запуске открывается меню с пустым инвентарём. Ввод выполняется только с клавиатуры:

- `1` - добавить велосипед;
- `2` - добавить электровелосипед;
- `3` - добавить шлем;
- `4` - добавить зарядную станцию;
- `5` - показать все предметы, их количество, расход энергии и транспорт для новичков;
- `0` - завершить работу.

При добавлении программа запрашивает название и положительный целый инвентарный номер. Для транспорта также вводятся удобство (1-10) и исправность (`1` - да, `0` - нет), для потребителей энергии - суточный расход. Дробные числа можно вводить с точкой или запятой. Неверный ввод вызывает повторный запрос того же поля. Ctrl+D завершает ввод; незаконченный предмет не добавляется. Данные хранятся в памяти до выхода, чтения и записи файлов нет.

Меню реализовано в [ConsoleMenu.cs](ConsoleMenu.cs). В [Program.cs](Program.cs) сохранён последовательный демонстрационный сценарий, доступный через `--demo`. Ниже описаны его данные и результаты.

| Предмет | Номер | Состояние | Удобство для новичков | Энергия за сутки, кВт·ч |
| --- | --- | --- | --- | --- |
| Городской велосипед | 1 | Исправен | 8 | Не потребляет |
| Сломанный велосипед | 2 | Неисправен | 9 | Не потребляет |
| Электровелосипед | 3 | Исправен | 4 | 1,5 |
| Защитный шлем | 4 | Не применимо | Не применимо | Не потребляет |
| Зарядная станция | 5 | Не применимо | Не применимо | 2 |

Ожидаемый результат основного сценария приёма:

- городской велосипед, электровелосипед, шлем и станция приняты;
- сломанный велосипед отклонён и не участвует в отчётах;
- в инвентаре 4 предмета;
- общее потребление составляет 3,5 кВт·ч в сутки;
- новичкам подходит городской велосипед;
- в полном списке отображаются номера 1, 3, 4 и 5 вместе с названиями.

Перед основным сценарием выводится отчёт по пустому инвентарю: 0 предметов, 0 кВт·ч и отсутствие подходящего транспорта для новичков.

После основного сценария добавляются исправный велосипед с показателем 5 и электровелосипед с показателем 6 и нулевым потреблением. Оба принимаются в парк, но в список для новичков из этой пары попадает только электровелосипед. Всего становится 6 предметов, потребление остаётся равным 3,5 кВт·ч в сутки. Новичкам подходят городской велосипед и электровелосипед с показателем 6.

Далее программа пытается создать велосипеды с удобством 0 и 11, а также электровелосипеды с отрицательным потреблением, `NaN` и бесконечностями. `try/catch` перехватывает `ArgumentOutOfRangeException` для каждой попытки и выводит сообщение. После ошибок программа продолжает работу и показывает итоговый отчёт: некорректные объекты в инвентарь не попали, в нём осталось 6 предметов.

Десятичный разделитель и обозначения специальных чисел в консоли зависят от региональных настроек системы. Эти сценарии также проверяются юнит-тестами на уровне доменной модели и сервисов.

## 4. Доменная модель и принятые решения

### Инвентарь

[IInventoryItem](Domain/IInventoryItem.cs) задаёт свойства `Name` и `Id`. В этой модели `Id` используется как инвентарный номер. Интерфейс позволяет учитывать разные виды предметов через общий контракт.

[InventoryItem](Domain/InventoryItem.cs) хранит имя и номер. Класс абстрактный: создаются конкретные предметы, а не неопределённый инвентарь. Свойства доступны для чтения, значения устанавливаются в конструкторе.

Список в `InventoryService` имеет тип `List<IInventoryItem>`. Поэтому новый предмет может как наследоваться от `InventoryItem`, так и самостоятельно реализовать интерфейс. Сотрудники не считаются инвентарём и не должны наследоваться от этого класса только ради повторного использования имени и номера.

### Транспорт и вещи

[Vehicle](Domain/Vehicle.cs) наследуется от `InventoryItem` и добавляет `BeginnerFriendliness` и `IsOperational`. От него наследуются [Bicycle](Domain/Bicycle.cs) и [ElectricBicycle](Domain/ElectricBicycle.cs).

Показатель удобства должен находиться в диапазоне от 1 до 10 включительно. Некорректное значение вызывает `ArgumentOutOfRangeException`. Неисправный транспорт можно создать как объект: это позволяет передать его на осмотр и получить отказ в приёме.

[Helmet](Domain/Helmet.cs) и [ChargingStation](Domain/ChargingStation.cs) напрямую наследуются от `InventoryItem`. Отдельный промежуточный класс для вещей пока не нужен: общего состояния сверх имени и номера у них нет.

### Потребление энергии

[IEnergyConsumer](Domain/IEnergyConsumer.cs) задаёт свойство `DailyEnergyConsumption`. Его реализуют электровелосипед и зарядная станция. Обычный велосипед и шлем этот интерфейс не реализуют.

Потребление хранится в `double`, измеряется в кВт·ч за сутки и должно быть конечным неотрицательным числом. Ноль допустим; отрицательные числа, `NaN` и бесконечности отклоняются. Расчёт суммирует значения через `IEnergyConsumer`, поэтому учитывает также зарядные станции.

### Приём и отчёты

[IServiceCenter](Services/IServiceCenter.cs) задаёт метод `Inspect(Vehicle vehicle)`. Реальный [ServiceCenter](Services/ServiceCenter.cs) принимает решение по `IsOperational`. Это выбранное упрощение технического осмотра: программа не моделирует датчики и отдельные неисправности.

[InventoryService](Services/InventoryService.cs) получает `IServiceCenter` через конструктор. `AddVehicle` добавляет транспорт только после положительного решения и возвращает `bool`, показывающий результат приёма.

`AddItem` направляет транспорт в `AddVehicle`, а вещи добавляет напрямую. Поэтому общий метод добавления не позволяет обойти осмотр транспорта.

Отчёт для новичков выбирает из принятого инвентаря только `Vehicle` с показателем не ниже 6. `GetAllItems` возвращает отдельный список со ссылками на предметы: изменение этого списка не меняет внутреннюю коллекцию сервиса. Сами предметы при этом не клонируются.

## 5. Применение SOLID

### SRP - разделение ответственности

Доменные классы описывают предметы и допустимые значения. `ServiceCenter` отвечает за решение техосмотра. `InventoryService` хранит принятые предметы и предоставляет операции учёта. `SimpleContainer` создаёт сервисы. `Program.cs` связывает компоненты и выводит результат.

### OCP - расширение без массовой правки

Для нового вида транспорта можно создать наследника `Vehicle`. Если он потребляет энергию, он также реализует `IEnergyConsumer`. Методы приёма, суммирования энергии и выборки для новичков работают с этими общими контрактами и не перечисляют конкретные классы транспорта.

Это не обещание отсутствия любых изменений: новый тип нужно создать в демонстрационном сценарии. Если изменятся сами правила осмотра или критерий для новичков, соответствующую логику потребуется пересмотреть.

### LSP - подстановка наследников

`Bicycle` и `ElectricBicycle` можно передавать в методы, принимающие `Vehicle`. Оба сохраняют общий смысл номера, исправности и диапазона удобства. Для добавления электровелосипеда не требуется отдельная версия `AddVehicle`.

### ISP - небольшие интерфейсы

`IInventoryItem`, `IEnergyConsumer` и `IServiceCenter` описывают разные возможности. Шлем не обязан иметь фиктивное энергопотребление, а зарядная станция не обязана иметь показатель удобства прокатного транспорта.

### DIP - зависимость от абстракции

`InventoryService` зависит от `IServiceCenter`, а не создаёт конкретный `ServiceCenter` внутри себя. Реализация выбирается снаружи и передаётся в конструктор. Тесты могут заменить её заглушкой без изменения бизнес-логики.

### Какой принцип проявляется наиболее явно

Наиболее явно применён DIP в конструкторе `InventoryService`. Его практическая польза показана в `DependencyInjectionTests`: контейнер передаёт тестовую реализацию техосмотра, и результат приёма меняется согласно её решению.

### Какой принцип сознательно ограничен

SRP применён с ограничением: `InventoryService` совмещает хранение коллекции, добавление предметов и простые отчёты. В небольшом приложении все эти операции относятся к одному инвентарю, а выделение отдельного класса под каждый короткий расчёт усложнило бы решение.

Если появятся база данных, экспорт или сложные отчёты, хранение можно вынести в репозиторий, а отчёты в отдельный сервис. Сейчас такое разделение не реализовано. Проверки допустимого потребления в двух конструкторах также оставлены явно, без дополнительной иерархии ради нескольких одинаковых строк.

## 6. DI-контейнер

В проекте используется собственный [SimpleContainer](Infrastructure/SimpleContainer.cs). Он поддерживает регистрацию функций создания и время жизни singleton: один экземпляр зарегистрированного типа на конкретный контейнер.

`RegisterSingleton<TService>` сохраняет функцию создания. `Resolve<TService>` при первом запросе вызывает эту функцию и сохраняет результат. При последующих запросах возвращается тот же объект.

Регистрации находятся в `Program.cs`. Используются именованные функции `CreateServiceCenter` и `CreateInventoryService`. Последняя получает `IServiceCenter` через контейнер и передаёт его конструктору `InventoryService`. Лямбды не используются.

Сам `InventoryService` не обращается к контейнеру и получает зависимости явно. Контейнер используется при сборке объектов в `Program.cs` и в проверках DI.

Контейнер отклоняет повторную регистрацию типа, отсутствующую регистрацию, `null` вместо функции и `null` в результате её выполнения. Он предназначен для текущего однопоточного консольного сценария. 

## 7. Расширение системы

### Новый вид транспорта

Например, для электросамоката можно добавить `Scooter : Vehicle, IEnergyConsumer`, реализовать хранение потребления и создать объект в сценарии. При сохранении существующих контрактов `InventoryService` сможет принимать его, учитывать в энергии и выбирать для новичков без изменений своих методов.

### Сотрудник

Для сотрудника потребуется отдельная модель и сервис учёта. Сотрудник не реализует `IInventoryItem` и не попадает в инвентарную коллекцию. Существующие отчёты по вещам и транспорту менять не нужно, но для сотрудников понадобятся собственные операции.

### Склад запчастей

Отдельную пронумерованную деталь можно представить как `IInventoryItem`. Для складских остатков по количеству, партий, поступлений и списаний потребуется отдельная модель склада: текущий инвентарь учитывает индивидуальные предметы, а не количество одинаковых деталей. Существующий учёт транспорта при этом может остаться без изменений.

## 8. Тестирование

Используются xUnit и `coverlet.collector`. Тесты организованы по Arrange, Act, Assert: подготовка, действие, проверка. Для проверки исключений `Assert.Throws` совмещает выполнение действия и проверку результата.

Каждый тест создаёт собственные объекты. Проверяются публичные результаты, а не содержимое приватных полей. Набор покрывает успешный и неуспешный приём, вещи, пустой инвентарь, энергию, границы удобства и поведение контейнера.

### Какие тесты фиксируют ключевые правила

- `AddVehicle_WhenInjectedServiceRejects_DoesNotAddVehicle` регистрирует `RejectingServiceCenter` вместо настоящего сервиса. Исправный велосипед отклоняется, инвентарь остаётся пустым.
- `AddVehicle_WhenInjectedServiceAccepts_UsesItsDecision` проверяет, что решение действительно делегировано внедрённому сервису. Разрешающая заглушка используется только в тесте.
- `AddItem_WhenInjectedServiceRejects_DoesNotBypassInspection` защищает общий метод добавления от обхода осмотра.
- `GetBeginnerFriendlyVehicles_WhenRatingIsFive_ReturnsEmpty` и `GetBeginnerFriendlyVehicles_WhenRatingIsSix_IncludesVehicle` фиксируют включённую границу 6.
- `GetTotalDailyEnergyConsumption_WhenInventoryIsMixed_SumsEnergyConsumers` проверяет суммарный расход транспорта и станции.
- `Resolve_WhenSingletonIsRequestedTwice_ReturnsSameInstance` проверяет возврат одного экземпляра при повторных запросах.

Тестовые заглушки задают ответы `Inspect`; количество его вызовов не проверяется. Для обычных проверок сервиса применяется также прямая передача зависимости через конструктор. Это DI без обязательного использования контейнера в каждом тесте.

Помимо 44 проверок модели, сервисов и контейнера, добавлена одна сквозная проверка консольного сценария. Она запускает точку входа приложения с параметром `--demo`, перехватывает вывод и проверяет, что после некорректных данных появился итоговый отчёт с 6 предметами и расходом 3,5 кВт·ч. После проверки стандартный вывод восстанавливается. Консольные тесты выполняются без параллельного запуска с другими тестами, поскольку `Console.In` и `Console.Out` общие для процесса. Дополнительные проверки меню подают строки через `StringReader`, перехватывают вывод и проверяют итоговый инвентарь. Стандартные потоки и изменённые региональные настройки восстанавливаются через `finally`.

## 9. Текущие ограничения

- Данные находятся в памяти и не сохраняются между запусками.
- Технический осмотр упрощён до проверки `IsOperational`.
- Порог для новичков равен 6 и задан в `InventoryService`.
- Уникальность инвентарных номеров и повторное добавление одного предмета пока не проверяются. Меню требует непустое имя и положительный номер; доменная модель этих ограничений не устанавливает. В демонстрации номера уникальны.
- Показатель удобства и потребление проверяются в конструкторах и при вводе через меню. Ошибки демонстрационных данных перехватываются в `Program.cs`.
- Количество предметов в отчёте включает и транспорт, и вещи.
